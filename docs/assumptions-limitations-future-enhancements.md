# Assumptions, Limitations & Future Enhancements

## Assumptions

- **The reviewer, not the AI, owns the final decision.** The pipeline produces a recommendation and a risk analysis, not a binding approval/rejection. The human review workflow (edit metadata, accept/reject individual risk findings, comment, record a final decision) is treated as a required step in the intended usage, not an optional add-on — this is why every review action is written to the same audit trail as the AI's own actions.
- **Input contracts are in English and machine-readable text (or text-extractable PDF/DOCX).** Scanned/image-only PDFs with no embedded text layer will extract as empty or near-empty text and fail the Node 3 minimum-length gate (`POL-EXT-001`) rather than silently producing a garbage analysis.
- **One contract, one pipeline run, one reviewer at a time.** There's no multi-user concurrency model — no per-user auth, no concept of "assigned reviewer," no locking. Any client can call any endpoint for any contract ID.
- **A single evaluation/demo process, not a fleet.** All state is scoped to one running Node process. This is treated as acceptable for a take-home-sized deliverable evaluated by running the app locally, not as a production deployment assumption.

## Known limitations

- **In-memory persistence only — nothing survives a restart.** Executions, review state, the audit trail, agent config versions, and continuous-learning traces all live in process memory (`Map`/array-backed stores). Restarting the backend process discards all history. This was a deliberate scope decision (see `arch.md`/the original plan) rather than an oversight — introducing a database was explicitly out of scope for this deliverable so effort could go toward the AI pipeline, the governance dashboard being genuinely computed, and the review workflow instead of persistence-layer plumbing.
- **The audit trail is capped at 200 entries.** `governance-audit-store.ts` keeps the most recent 200 hash-chained events; older entries roll off. For a long demo/evaluation session with many contracts, the oldest audit evidence for the earliest runs will no longer be visible in `GET /api/v1/governance/audit`, though the policy *fire counts* the dashboard shows are still counted correctly against whatever remains in the window at query time — they are not a running total independent of the cap.
- **Single LLM provider, no fallback model.** If OpenRouter is unreachable, the configured model is deprecated, or (concretely observed during development) the free-tier daily rate limit is exhausted, every contract analysis that reaches Node 3 onward fails gracefully (`status: 'error'`, no crash) but produces no result. There is no automatic fallback to a second model or provider.
- **Free-tier model quality ceiling.** The default model, `google/gemma-4-26b-a4b-it:free`, is chosen for zero-cost evaluation, not maximum extraction/reasoning quality. `callJsonLLM`'s retry-on-invalid-JSON logic exists specifically because smaller free-tier models are less reliable at strict JSON-schema-following than top-tier paid models; expect occasional retries in normal operation, and expect meaningfully better extraction/risk nuance from a stronger paid model behind the same code path.
- **No file size or contract length ceiling beyond the 60,000-character truncation.** A contract longer than that is truncated and the analysis is explicitly flagged (`truncated: true`, surfaced in the execution record and an audit event) but the truncated tail is never analyzed. There is no chunking/map-reduce strategy for very long contracts.
- **No authentication or authorization anywhere.** Every API endpoint (including all governance and review endpoints) is unauthenticated. This is acceptable for local evaluation, not for any shared or internet-facing deployment.
- **Duplicate detection is exact-content only.** It hashes extracted text with SHA-256, so it catches byte-identical re-uploads (including the same file re-uploaded under a different filename) but not near-duplicates — a contract with one word changed, or the same contract re-typed rather than re-uploaded, will not be flagged.
- **The confidence scores are heuristic, not calibrated against ground truth.** `extraction`/`clause_identification`/`summary` confidence are structural completeness proxies (fraction of fields filled, fraction of clauses evidenced) rather than statistically calibrated probabilities, and `risk_detection` confidence is simply the model's own self-report. None of the five scores have been validated against a labeled dataset of correct vs. incorrect extractions — see "Future enhancements" below.
- **No structured redlining or clause-rewrite suggestions.** The system identifies and explains risks; it does not propose replacement contract language.

## Future enhancements

- **Persistent storage.** Swap the in-memory stores (`execution-store.ts`, `review-store.ts`, `governance-audit-store.ts`, `agent-config.service.ts`) for a real database, keeping their existing method surfaces (`get`/`save`/`list`/`record`) so the pipeline, controllers, and governance service code would not need to change — only the storage implementation behind those interfaces.
- **Multi-provider / fallback model support.** Add a secondary OpenRouter model (or a second provider entirely) that the pipeline falls back to automatically when the primary model errors or rate-limits, with the choice itself recorded in the audit trail so a reviewer can see which model actually produced a given analysis.
- **Calibrate confidence scores against real outcomes.** Use the human review workflow's `riskDecisions` (accepted vs. rejected findings) and `finalDecision` as ground truth to measure how well `risk_detection`/`overall` confidence actually predicts reviewer agreement, feeding that back through the continuous-learning engine's `risk_score_calibration` quality target rather than leaving it as an unvalidated heuristic.
- **Chunking for very long contracts.** Replace the hard 60,000-character truncation with a map-reduce extraction strategy (extract per-section, merge/deduplicate metadata and clauses) so a 100-page master agreement is fully analyzed rather than partially analyzed with a `truncated` flag.
- **Near-duplicate / clause-level diffing.** Extend duplicate detection beyond exact-hash matching to semantic similarity, so amended re-submissions of a mostly-unchanged contract can be flagged and diffed against the prior version rather than analyzed from scratch.
- **Authentication, per-user review assignment, and multi-tenant isolation** for any deployment beyond a single-evaluator local demo.
- **Structured redline suggestions.** Extend Node 4/5 (or add a Node 6) to propose specific replacement or additive clause language for high-severity risks, not just flag and explain them.
- **Real-time collaborative review.** Multiple reviewers on the same contract with live-updating comments/decisions, rather than the current last-write-wins model.

## Environment caveat encountered during development (documented for transparency)

While exercising the pipeline repeatedly during development, Node 3 returned a genuine OpenRouter error: `429 Rate limit exceeded: free-models-per-day. Add 10 credits to unlock 1000 free model requests per day`. This is expected behavior under the free-tier model's daily quota, not a defect — the pipeline correctly caught it, recorded it to the audit trail, and returned a graceful `status: 'error'` execution record rather than crashing. Anyone re-running the demo extensively on the same free API key/model should expect to encounter this and should either wait for the daily quota to reset, add OpenRouter credits, or switch `OPENROUTER_MODEL` to a different (or paid) model.
